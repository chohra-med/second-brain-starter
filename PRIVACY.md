# Privacy boundary

Second Brain Starter is a local source package. Its initializer reads only the package manifest, the managed files it names and its own `.second-brain/` records. It does not recursively read a parent folder, inspect unrelated project files, read `.env` files or credentials, or send project content anywhere. The exceptions to that read limit are `workspace-plan` and `connect`, described in the next two paragraphs. Neither one sends anything.

`workspace-plan` reads one folder you name, the parent folder. It resolves that path once and then follows no link inside it. It lists the folders directly inside the parent, and for each one it checks by name and type whether a real `.git` folder sits directly under it. It does not open that `.git` folder, and it does not list or read anything inside a child, a nested folder or a repository. It also checks whether a `Second Brain` folder already exists in the parent, without reading inside it. It reads no file content. It writes nothing, starts no program and sends nothing. It prints the parent path, the proposed workspace path, the repository paths and the names of any folders it could not read to your terminal. Nothing it prints is stored.

`connect` reads only the repository you name, and only these things. At the repository root it checks by name and type whether these exist: the files `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `RULES.md` and `SPEC-HARNESS.md`; the folders `ai_rules/` and `.memory/`; and the harness receipt `.claude/agents/.init-synthesis.json`. It lists the names in `.claude/agents/` and keeps the ones that match `sdd-*.md`. It checks whether `.git/` and `.git/config` exist. When `.git/config` is a regular file, it reads the `origin` URL from it. It checks whether each path it plans to write already exists, and it reads those bytes only to compare their hashes. It never prints or stores those bytes. It never lists or reads the contents of a sibling or parent folder, or of another repository. When the vendored Spec Harness registers its edit guard, `connect` also reads `.claude/settings.local.json` to merge one hook entry into it, and writes that file back with its content and the entry. When it does not register the guard because the hook file there differs or is not executable, it reads `.claude/settings.local.json` and the committed `.claude/settings.json` only to see whether either already holds the entry. It follows no link to them and writes nothing to them. In a repository whose `.git` folder holds `HEAD`, `objects` and `refs`, it reads `.git/info/exclude` only to see whether that file already has the line `/.claude/settings.local.json`, and adds the line when it does not. It adds the line even when git already tracks or ignores the settings file; the line is harmless then. It does not read `.git/index` or any `.gitignore` file for this. When the repository has no such `.git` folder, it checks by name and type whether a `.git` exists in each parent folder, and reads nothing there. If `.git/config` exists but is not a regular file, `connect` refuses that repository. Verify reads the bytes of the staged files it wrote, only to compare their hashes. Apart from `.git/config`, those comparisons and the registration reads above, `connect` reads no repository file contents.

The installer rejects unsafe targets, target escape, symlinked destination ancestors, and ordinary differing managed files. It appends the managed block to a root `AGENTS.md` or `CLAUDE.md` that has no install record. It refuses to change a loader file whose comment is broken: a comment that is never closed, or a comment that names the tool and is not the one clean managed block, stops the install. A plain sentence that names the tool, outside any comment, does not stop it. `.gitignore` follows the same rule, with a line that starts with `#` as its comment, and only a `#` line shaped like a marker counts. A root `AGENTS.md`, `CLAUDE.md` or `.gitignore` that has a null byte, or starts with a UTF-16 or UTF-32 byte-order mark, stops the install too. A legacy single-byte encoding is not detected, and the initializer appends to it like plain text. The tool cannot recognise every possible damage, so read the plan before you approve it. These are filesystem checks performed by the initializer. For the repository you name, `connect` applies the path-safety checks: it refuses a path with a symlink in it, the workspace itself, a folder inside the workspace, a folder that contains the workspace, the home directory, the filesystem root and the source copy. Apart from the edit guard entry in `.claude/settings.local.json` and the line in `.git/info/exclude`, it never overwrites a file in the repository. A file that already exists there is kept and listed. Markdown instructions for an AI client are different: they guide a client that has already been given local-file access. They do not grant access, sandbox a client, enforce compliance, or support every future client version.

The installed target stores state, backups, and transaction-scoped rollback receipts under `.second-brain/`. Those local records include managed relative paths, hashes, and receipt identifiers. Connection records, connect receipts and connect pending records also hold the absolute path of the workspace and of each repository you explicitly connected with `connect`. Those paths can include your home folder. A connection also has a `Connection.md` file in its folder under `01-Projects/`, inside the workspace. That file holds the repository path, the remote, the rule-file names found, and the Spec Harness version and commit. The remote is the `origin` URL with credentials, query and fragment removed. A remote the parser does not recognise is recorded as `unknown`. Git writes some URLs in quotes (for example, when they contain `#` or `;`), and the loader does not read quoted values, so those are recorded as `unknown`. A hand-written, unquoted URL is parsed and stripped. Apart from these fields, `connect` records nothing from a repository. It records no file contents. While it runs, it keeps one temporary copy: before it merges the edit guard entry into a `.claude/settings.local.json` that already exists, it copies that file into the workspace, at `.second-brain/backups/<receipt ID>/repo/.claude/settings.local.json`, so that a connect that fails or is interrupted can give the file back byte for byte. A settings file can hold local permissions and environment values, so connect deletes the copy as soon as it finishes, or once it has undone a failed or interrupted connect. If connect is stopped after it finished but before it deleted the copy, `verify` lists the copy as `RESIDUE`, and the next approved connect, rollback or recovery deletes it. Until then the privacy block makes git ignore it, as all of `.second-brain/`, but a copy of the workspace folder carries it. The tool does not inspect the recorded names or paths for sensitive content. Those records stay on your machine and are not part of the shipped template. Folder names can carry client names, and the tool does not check them. The project index, `01-Projects/Index.md`, has one row for each connected project in a workspace that has that index. The row names the project and links its `Connection.md`, and it holds no path. A workspace connected by a build from before this change keeps the older row, which stores the repository path in its third column. Connect leaves an existing row for the same name as it is, so remove the path from that row by hand. The row's link to `Connection.md` does not resolve in a fresh git clone, because git ignores that file.

**Upgrade.** `upgrade` reads each managed file and seed file the manifest names in your workspace, and the base snapshots under `.second-brain/base/`. It writes a base snapshot for each managed or seed file whose snapshot differs from the current template. Each snapshot holds the template bytes of the version it records, and none of your text. It also reads the bases of earlier releases bundled in the source copy. For a seed file you edited whose template changed, `upgrade` plans a proposal under `.second-brain/merge/<version>/`. That proposal contains your text and the new template text. For a seed path that is new in this release and already holds your file, the proposal holds the template text alone, and your file stays as it is. Planning reads any proposal already at that path and writes nothing. The approved apply writes the base snapshots and the proposals, and it writes a proposal only where no file exists yet. `upgrade --proposal PATH` prints one proposal to your terminal and writes nothing. The privacy block makes git ignore `.second-brain/`, so a git clone does not carry these files. A copy of the folder does.

**Quick start.** The quick start procedure (`03-Resources/Procedures/quick-start.md`) gives instructions to your AI client. It is not a command in this package. For one repository you name, the client reads only these items, when they exist: `AGENTS.md`, `RULES.md`, `CONTRIBUTING.md`, the folders `ai_rules/` and `.memory/`, and `README.md`. `connect` does not check `README.md`; the client reads it under this procedure. When a repository has no Spec Harness files, `connect` also reads an existing file at each path it would write, such as `AGENTS.md`. It reads those bytes only to compare their hashes with the file it would write. It never prints them, stores their content or sends them anywhere. This package sends nothing. The client sends what it reads to its model provider, under that client's own settings. After you approve the exact text, the client writes three drafts into the project folder in your workspace: `FACTS.md`, `roadmap.md` and a first entry in `progress.md`. Those three files are not in the privacy block, so git tracks them, and a pushed or shared workspace carries them. `connect` creates that project folder from the template files before the drafts are written. In a repository with no Spec Harness files, an approved `connect` also writes up to 114 harness files and 46 folders into that repository. A file that already has the same name is kept. The new files stay uncommitted, and your team decides whether to commit them. `rollback`, with the receipt ID that `connect` prints, removes them. If you have edited one of them, `rollback` refuses and removes nothing. From a `.claude/settings.local.json` that existed before, it takes out only the edit guard entry; the other keys and values stay. The exclude line that `connect` added comes out, and the rest of that file stays.

Sharing a copy of the workspace folder shares those paths and the `Connection.md` files with whoever receives it. The privacy block makes git ignore `Connection.md` by default, but a copy or an archive still includes it. Roll a connection back before you share a copy, or share the workspace only with people who may know those paths. The privacy block also ignores `00-Meta/Profile.md` and `00-Meta/Daily-Task-Plan.md`. A clone of your workspace made with git will not contain those two files, so the links to them on Home will not resolve in that clone until you add an exception line or copy the files.

The package has no telemetry, analytics, network service, global install, background process, or permission change. Node.js runs the initializer from the source copy you choose. The package runs locally and sends nothing anywhere. Its bundled folders are copied files, and the installer never runs them. The package's own test suite runs one of them, the usage dashboard script, only on fake transcript folders that the tests build. `init` does not install the optional `api-anything` skill. An upgrade from v1.8.0, v1.9.0 or v1.10.0, which installed it, leaves it in place and still active until you delete `.claude/skills/api-anything/` and `.agents/skills/api-anything/` in your workspace. When it is there, because you added it by hand or an upgrade left it, it tells your AI client to run an outside command, which `npx` can fetch from that project's default branch and run without asking, and whose `login` step can import cookies from your everyday browser. This package never runs that command; your client does, when it follows the skill. Once your AI client reads a repository's files, what it sends to its model provider is governed by that client and its settings, not by this package. Before sharing a modified copy, run `node --test`, which includes the package scan. If the scan fails, the test named `the real source root, vendored bytes included, passes the package scanner against FILE-ALLOWLIST.txt` lists each finding as a rule and a relative path, for example `UNALLOWLISTED_MEMBER .DS_Store`. Review that complete list before you share anything. The scan reports rules and relative paths only, never matched secret text.

**Usage dashboard.** The package ships the script `usage-dashboard.mjs`. The installer never runs it. The package's own tests run it only on fake transcript folders that they build. You, or your AI client, run it from the skill folder. By default it reads only the `*.jsonl` transcript files under the Claude Code projects folder in your home folder, and the `subagents` folders inside them. If you name another folder with `--projects-dir`, it reads only the `*.jsonl` files under that folder instead. It also opens one price file, the `usage-prices.json` beside it or the one you name with `--prices`. The default projects folder is outside the workspace. A folder you name with `--projects-dir` may not be. The price file beside the script is inside the workspace once the skill is installed. Apart from the files the installer, the package scan and the test suite read from the source copy, the temporary folders the test suite builds, the repository you name with `connect`, and the parent folder you name with `workspace-plan`, the usage dashboard is the only part of the package that reads files outside the workspace. It does not follow a symbolic link below the projects folder. The projects folder you name is read even when it is itself a link. It prints counts, token sums, cost estimates, dates, session ids, project folder names (Claude Code builds those from folder paths, so one can show a client or project name), the disk paths of the projects folder, the price file and any file with bad input, and skill, command and model names of a fixed shape. It prints no prompt, answer, tool input or tool result. It opens no network connection, starts no program and writes no file. When an AI client runs it, the client sends the printed output to its model provider under the client's own settings. Unlike `skill-creator`, which the v1.4.0 entry left out because it runs local scripts and sends content to a model provider, this script, by itself, sends nothing anywhere, starts no program, writes no file, and the installer never runs it. Its printed output holds numbers, session ids, folder names and disk paths, never conversation text, apart from skill, command and model names of a fixed shape.

Keep local projects private when they contain private information. A plain Markdown workspace can be copied as easily as any other local files.
