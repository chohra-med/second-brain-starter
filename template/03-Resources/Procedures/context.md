## ICM change contract

Before changing a rule, command, skill, workflow, automation, handoff, or context route, record:

- Owner: one canonical file remains authoritative.
- Context: list only files the task needs; follow the selected-project route above.
- Effects: name the permitted changes and excluded effects.
- Evidence: name a completion check and a failure case that must be rejected.
- Continuity: preserve user-owned records and name the recovery path.
- Learning: route confirmed misses through [learning and scaling](learning-and-scaling.md), then verify the correction in a fresh session.

Reuse unchanged files already read in this task. Read additional files only when the task needs them; no token target overrides a required source.

## Architecture maintenance safeguards

Apply this section when changing system architecture: rules, commands, skills, workflows, automations, handoffs or context routing. Ordinary note work uses the compact context note above.

Keep durable README maps pointed at current owners. Name affected readers and writers before moving an owner or changing its contract; maps own navigation, never copied facts. PARA owns filing, CODE owns knowledge processing, and SDD owns execution.

For each stage, name scoped inputs, expected outputs and the check that closes it. Reuse unchanged reads; justify expansion with a named missing dependency. Required project rules, correctness and privacy context must remain available even when optimizing context size.

Keep handoffs concise: owner and required rules, source revision, permitted effects, evidence and one next action. Preserve source identities, exact preimages, destination and case-sensitive link state, concurrent user work and a recovery path. Never delete memories or logs or mass-rename linked records.

Graph or semantic discovery is optional, scoped and non-authoritative. Confirm a discovered claim against its current source owner before acting; stale discovery is not evidence.

Compare performance only across a named task, model, client, inputs and output-quality criteria. Record actual available provider usage and latency separately from file bytes or estimates. Label unavailable evidence and do not claim savings from smaller files alone.

Keep approval, retry, stop and recovery boundaries explicit. A failure case must be planted and rejected before trusting a check. Stop on conflicting sources, unexpected effects or failed recovery preconditions; preserve user work and route the unresolved decision to its owner. File instructions do not enforce client compliance or prove native skill loading.
