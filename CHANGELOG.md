# Changelog

## v1.5.0 (2026-10-13)

- Adds the shared skill `usage-dashboard`, installed to `.agents/skills/` and `.claude/skills/`. It is one script, `usage-dashboard.mjs`, that reads the Claude Code transcript files on this machine and prints, per session, the tokens used, an estimated cost at list prices, the peak context, and how often each skill and slash command was used. The skill is written for this repository, see [ATTRIBUTION.md](ATTRIBUTION.md).
- `usage-prices.json` beside the script is a seed file. Each install writes it once. It is yours to edit, and an upgrade keeps your copy. The plan shows `IDENTICAL` for an unedited copy under an unchanged template, and `PERSONALIZED` once you edit it. A later template change reaches an unedited copy as `SEED-UPDATE`, and an edited copy as `PERSONALIZED` with the template's version offered as a proposal.
- The installed skill set grows from fourteen to fifteen. The README, the two docs that count the skills and the installer test now say fifteen.
- Design decision, usage dashboard (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): this is the first file in the template that is meant to be run. It is a script and not a procedure an assistant follows, because the counting must be exact and the same every time: the same transcripts give the same numbers, and a bad line is named by file and line instead of being skipped by a reader's judgement, except a last line with no line ending, which is skipped and not reported. Its limits: it reads only Claude Code transcript files, in the `.claude/projects` folder of your home folder or the folder you name with `--projects-dir`, and the one price file; it prints aggregates, session ids, project folder names, disk paths and names of a fixed shape, never prompt, answer, tool input or tool result text; it opens no network connection, starts no other program, writes no file and needs no dependency beyond Node.js 22 or newer; and the installer never runs it, while the package's own tests run it only on fake transcript folders that they build. Prices are a seed file the user owns, and every money figure is an estimate at list prices, which may differ from a bill. It does not do these things: no chart, no web page, no background job, no telemetry.
- `PRIVACY.md` has a new paragraph that says what the script reads and prints, that it opens no network connection and writes no file, and that an AI client which runs it sends the printed output to its model provider under the client's own settings.
- `test/usage-dashboard.test.mjs` runs the script's tests against this repository's copy and adds three: a fresh install that verifies, a verify after the installed price file is edited, and the installed script run on a planted transcript folder (exit 0, then exit 1 naming the file and line, then exit 0 once restored). The symbolic link test skips with a message when the system will not create a link.
- `test/installer.test.mjs` lists the new skill, and the two installed price files as seed files, in its exact lists.
- Version: the source moves from `v1.4.1` to `v1.5.0` in `VERSION`, `package.json`, the manifest's `templateVersion`, the CLI help line and the README.
- Design decision, `status` (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): `second-brain status --target PATH` is read-only. It names the installed template and receipt, this CLI's template, and the count of each state an upgrade would plan. It applies nothing; `upgrade` prints the full plan and its digest. Covered by `test/status.test.mjs`.
- Design decision, `workspace-plan` (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): `second-brain workspace-plan --parent FOLDER` reads that one folder and writes nothing. It lists each folder directly inside it that holds a real `.git` folder, and prints a `connect` command for each. It does not follow symbolic links or list nested folders. `--list-projects` prints only the repository paths. It names `Second Brain` as the workspace folder and does not create it. This reverses two earlier statements: "There is still no discovery" in v1.3.0, and the v1.4.0 statement that quick start never lists or searches for repositories. The quick start procedure keeps that limit: it works on one repository you name. The read scope is owned by [PRIVACY.md](PRIVACY.md). Covered by `test/workspace-plan.test.mjs`.
- Design decision, `verify --records` (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): a read-only lint of the workspace's records. It checks the status words in roadmap tables (`Open`, `In progress`, `Blocked`, `Done`, `Verified`), the progress entry limit of 10 and the record size limit of 15 KB. It changes nothing, merges nothing and pins nothing. Covered by `test/records.test.mjs`.
- Design decision, `verify --adopt PATH` (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): records the current bytes of a managed file as your accepted version. Without `--apply` it prints a plan with its own digest. The approved apply writes an adopt receipt, which `rollback` can undo. Only a managed file can be adopted: a seed file or a managed block is refused with `ADOPT_REFUSED`. It is the step after you resolve a `CONFLICT` by hand, and it is how a kept edit (`CUSTOMIZED-KEEP`) becomes the recorded version. Covered by `test/upgrade.test.mjs`.
- Design decision, the upgrade states (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): an upgrade compares the bytes you have, the template bytes the install recorded, and this release's template, and gives each path one state: `IDENTICAL`, `CREATE`, `MANAGED-UPDATE`, `SEED-UPDATE`, `CUSTOMIZED-KEEP`, `MERGE`, `PERSONALIZED`, `APPEND`, `CONFLICT` or `DEPRECATED`. The rules, and how to resolve each state, are in [Verify, update and roll back](docs/verify-update-rollback.md). This entry does not repeat them.
- Design decision, seed proposals (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): an upgrade never writes over a seed file you own. When this release's template changed a seed you edited, the plan shows `PERSONALIZED` and offers the template's version under `.second-brain/merge/<template version>/`, with conflict markers where your edit and the template's change overlap. A plan writes nothing. The approved apply writes that file, create-only, and its receipt lists it, so rollback removes it. A seed that is new at a path you already use keeps your file the same way. Seeds keep base snapshots of their template bytes, so the next proposal has a base. Reading a proposal: [Read a seed proposal](docs/verify-update-rollback.md#read-a-seed-proposal).
- Design decision, line merge (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): a managed file merges one line at a time, as git does. Two edits that touch the same line, or lines directly next to each other, are a `CONFLICT`, with the marked proposal printed by `upgrade --proposal PATH`. Edits with at least one unchanged line between them merge. This release has no word-by-word merge, because it writes sentences that neither side wrote. Covered by `test/merge3.test.mjs`.
- A managed file that is not UTF-8 text (it has a null byte, or starts with a UTF-16 or UTF-32 byte-order mark) is a `CONFLICT` with no proposal. The plan prints `Manual resolution required`, and the file stays as it is. A CRLF file merges in its own line endings. Covered by `test/merge3.test.mjs` and `test/upgrade.test.mjs`.
- Design decision, user-owned seed files (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): `Home.md` and `01-Projects/README.md` are seed files from this release, as are `01-Projects/Index.md` and the two `usage-prices.json` files. Before this release, `Home.md` and `01-Projects/README.md` were managed files. An unedited install still takes the new template as `MANAGED-UPDATE`, because its record says managed; after that upgrade the record says seed. An edited copy is merged when the edit does not overlap, and keeps your bytes with a proposal when it does. It is never a `CONFLICT`. Measured on scratch installs in [Upgrading to v1.5.0](UPGRADING.md#upgrading-to-v150).
- Design decision, multi-project route and project index (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): a second project is a copy of `03-Resources/_templates/project/` under `01-Projects/`, with one row added to `01-Projects/Index.md`. `workspace-plan` lists the repositories in one folder, and `connect` registers each one you name, with its own plan and digest. Each connect adds one row to the index, and its rollback removes exactly that row. No command reads a whole disk. The upgrade keeps your copy of `Index.md`, so a row that a development build of this release wrote may still hold an absolute repository path. Edit that row by hand to link `Connection.md`, as current rows do.
- The vendored Spec Harness is version 0.3.0, at commit `767d0727a4161d80c893191544423be42fcaab34`, under `vendor/spec-harness/` with its MIT `LICENSE`. Its pin is `vendor/SPEC-HARNESS-PIN.json`. Before this release it was 0.2.0 at commit `a663397c2aafa35071fb1fe899bd6a174cd423e6`. [CONTRIBUTING.md](CONTRIBUTING.md) describes the re-pin, and `tools/update-harness-pin.mjs` does the copy.
- `template-bases.json` is a frozen set of the managed and seed bytes of releases 1.1.0, 1.2.0, 1.3.0 and 1.4.0, keyed by SHA-256. It lets an install made before 1.5.0 merge against the template it was installed from. From 1.5.0, an apply records its own base snapshots under `.second-brain/base/`, so the file is not extended. It is planned for removal at 2.0.0. `tools/build-release-bases.mjs` rebuilds it from named sources. Covered by `test/release-bases.test.mjs`.

## v1.4.0 (2026-10-13)

- `init` and `upgrade` append the managed block to a root `AGENTS.md` or `CLAUDE.md` that has your text and no loader markers, when this tool has no install record for that file. The plan shows `APPEND`. Your bytes stay in front of the block, and rollback restores the file byte for byte. A root file with a broken comment shows `CONFLICT`, with the line number and the reason: a comment that is never closed, or a comment that names the tool and is not the one clean managed block. A plain sentence that names the tool does not. The same rule covers `.gitignore`, with `#` lines. The tool cannot recognise every possible damage, so read the plan before you approve it. An installed file whose markers were removed also shows `CONFLICT`. Known limit, not fixed here: appending to a file with CRLF line endings leaves mixed line endings, because the block is LF and your bytes are kept as they are.
- `verify` checks only the managed block of a root `AGENTS.md` or `CLAUDE.md`, and of `.gitignore`. Text you add above or below the block passes. A change inside the block, or a damaged or missing marker, is reported. Every other managed file is still compared whole.
- A root `AGENTS.md`, `CLAUDE.md` or `.gitignore` that is not UTF-8 text (a null byte, or a UTF-16 or UTF-32 byte-order mark) shows `CONFLICT` with a reason that says so, because the marker scan reads bytes. A UTF-8 byte-order mark is kept, and the block goes after the text.
- In `.gitignore`, only a `#` line shaped like a privacy marker outside the block counts as a damaged marker. A `#` comment such as `# second-brain notes` is your own text and does not stop the install.
- An installed `AGENTS.md`, `CLAUDE.md` or `.gitignore` that has lost a marker line, or its whole block, shows `CONFLICT` in the plan and fails `verify`. An installed file that is empty is different: `upgrade` stops before any plan, with one message that names the damage and the one way out, and exits 1. The plan has no `CONFLICT` line. `verify` prints `CORRUPT` for that file, with the same message, and exits 1. Each message names the damage, the line when there is one, and the one way out. [Install and recovery](docs/install-and-recovery.md#repair-a-damaged-loader-or-ignore-file) lists the way out for each case.
- A typed `no` at the approval prompt declines the plan in any folder and prints `Plan not applied.`, with exit code 0. Before, a typed `no` in a folder that was not empty printed a digest mismatch.
- Two refusal lines are clearer. An edited installed block says that its text differs from the block this tool installed, not that its markers are malformed. A refused rollback says the files differ from what this receipt wrote, not what `connect` wrote.
- At the terminal prompt, a new folder or an empty folder accepts a plain `yes` (or `y`, in any case, with spaces ignored) in place of the digest. Every other target still needs the exact digest. `--apply yes` is refused, and Enter, Ctrl-C and end of input are refusals as before.
- Design decision, append and one confirm (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): `init` and `upgrade` add the managed block after your own text in a root `AGENTS.md` or `CLAUDE.md` that has no install record, and rollback restores those bytes. The approval rule has one exception: a new folder or an empty folder takes a plain `yes`, because it holds no existing file that the plan could change. Every other folder needs the digest of the exact plan.
- Licence scope: the starter's own files are MIT-licensed. Bundled third-party folders keep their own licences, listed in [ATTRIBUTION.md](ATTRIBUTION.md). The `graphify` skill describes an outside tool that is separate software and is not bundled.
- Adds five shared skills, installed to `.agents/skills/` and `.claude/skills/`: `humanizer` copied unmodified from a pinned upstream commit (see [ATTRIBUTION.md](ATTRIBUTION.md)); `grill-me`, `readme-generator` and `graphify` written for this repository as generic skills; and `writing-skills`, a short guide to writing a skill. The `graphify` skill describes an optional outside tool that is not bundled. The installed set is twelve skills.
- `skill-creator` was evaluated and left out. It runs local scripts and sends content to a model provider, which the starter's privacy statement does not allow inside the bundle.
- Adds the procedure `03-Resources/Procedures/showcase-readme.md`, an example of three skills used in order to write a README for one project. The procedures index links to it.
- The install writes a managed `.gitignore` block, or appends it to your existing `.gitignore`. Git ignores the installer state, the daily notes in the daily notes folder (its shipped `daily-template.md` stays tracked), the Profile and Daily-Task-Plan seeds, and each project `Connection.md`. The plan prints these paths.
- Adds three ways to start, listed on Home in order from fastest to fullest, each a procedure in `03-Resources/Procedures/`: `quick-start.md` (index one to three repositories you name), `init.md` (five questions, saved one at a time) and `complete-init.md` (the full question set, in sections you can stop and resume). Each one shows its exact draft and writes only after a yes, and each ends with the same closing prompt.
- Design decision, starting layer for several projects (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): quick start is a procedure an assistant follows. It adds no command, no code that reads a disk and no dependency. It works one repository at a time, and only for a repository the person names. It runs the existing `connect` plan and approval for that repository, then reads only the rule files that [ONBOARDING.md](ONBOARDING.md) stage 9 names: `AGENTS.md`, `RULES.md`, `CONTRIBUTING.md`, `ai_rules/`, `.memory/` and `README.md`. It drafts that project's `FACTS.md`, `roadmap.md` and first `progress.md` entry, and writes them only after a yes. It never lists or searches for repositories, siblings, parents or home folders. A project with nothing readable is recorded as `Unknown`.

- `UPGRADING.md` now says that an install from an unreleased build with a `skill-creator` folder shows those files as `DEPRECATED` on upgrade, that nothing is deleted, and that a rollback may leave empty folders behind.
- `PRIVACY.md` now limits the non-UTF-8 refusal to what the code detects, a null byte or a UTF-16 or UTF-32 byte-order mark, and says that a legacy single-byte encoding is appended to like plain text. It also says `connect` is the one exception to the read limit, and that `connect` sends nothing.
- `test/append-and-privacy.test.mjs` has a table of the seven damaged states for `AGENTS.md`, `CLAUDE.md` and `.gitignore`. Each row checks the message in `verify` and in the plan, then the one way out, applied by hand, passes `verify`.

## v1.3.0 (2026-10-09)

- Design decision, multi-repository layer (recorded as [CONTRIBUTING.md](CONTRIBUTING.md) requires): `connect` is one digest-approved transaction over two roots, the workspace and one repository the person names. One plan and one digest cover both roots. Files in the repository are create-only: an existing file is preserved and listed, never overwritten, and never blocks the plan. Each applied connect writes a receipt that lists its files, and rolling back a receipt removes exactly the files it created in both roots, refusing if any of them changed. `connect` runs no subprocess and no git command. Connection records live in a new versioned `.second-brain/connections.json` beside the unchanged `installed-state.json`, so an install made by v1.x keeps its files and records, and nothing forces the hub shape. A v1.x install reports `SOURCE_MANIFEST_MISMATCH` from the 1.3.0 source until it is upgraded. There is still no discovery: each `connect` covers one repository that the person names.
- Vendors Spec Harness 0.2.0 at commit `a663397c2aafa35071fb1fe899bd6a174cd423e6` under `vendor/spec-harness/` with its MIT `LICENSE`, a pin record in `vendor/SPEC-HARNESS-PIN.json` and a test that checks each vendored file against the pin. The pin records the executable paths and recomputes the pinned git tree hash in Node, so a wrong tree, a stripped executable bit, a removed file or a swapped `LICENSE` fails `test/vendor.test.mjs`. `connect` reads the vendored manifest and copies the files it names. The vendored shell scripts are never executed. See [ATTRIBUTION.md](ATTRIBUTION.md).
- Adds a `00-Meta/Profile.md` seed and a missing-only Profile interview in `first-use.md`. It rewords Home, `00-Meta/AGENTS.md`, `01-Projects/README.md` and the context procedure so another project can sit beside the seeded `Selected-Project`. All seeds stay in the manifest. An upgrade plans a named CONFLICT if you already made your own `00-Meta/Profile.md`.
- Adds a real v1.2.0 install fixture, `test/fixtures/v1.2.0-install.json`, and tests that the current source verifies and upgrades it, and that `connect` leaves its installed state, verify result and bytes untouched.
- Adds `connect --target <workspace> --repo <repository> [--name NAME] [--apply DIGEST]`. It prints one plan for the workspace and the named repository, and writes nothing without the exact digest. A repository with no Spec Harness files gets the harness files staged and uncommitted, and reports STAGED until `/sdd init` writes its receipt. A repository that already has harness files is registered only, with no repository writes.
- `verify` states each connection from what is on disk: STAGED, INITIALISED, CHANGED (with counts of missing and differing staged files), MISSING, REGISTERED (with what detection finds now), or NO_RECEIPT, and prints the receipt ID on each `CONNECTION` line. It lists an interrupted or unfinished connect with its recovery command and makes `verify` exit non-zero. Leftovers are listed as RESIDUE and do not change the exit code. `rollback --receipt` reports recovered, completed and nothing-to-recover results in plain words.
- The connect and rollback refusals that have their own wording name a next command in the CLI tests, and so does the symlink refusal for init, upgrade, verify and rollback. A repository whose default name cannot be used says so and asks for `--name`. Printed commands use the absolute path of the script, so they run from any folder. They are quoted by platform: single quotes on macOS and Linux, double quotes on Windows, where `%` is not escaped.
- `init`, `upgrade` and `connect` print the exact apply command after the plan digest. Pressing Enter (empty input) at the approval prompt exits 0 for all three commands, printing `Plan not applied.`. Ctrl-C or end of input at the approval prompt exits 1 with `Plan not applied.` for all three commands. **Behaviour change:** before this version, `init` and `upgrade` exited 0 on Ctrl-C with no message. A run without a terminal that only plans prints `Plan only: nothing was applied.` and exits 0.
- Rolling back the workspace's own `init` or upgrade is refused while connections exist. The refusal prints the rollback command for each connection.
- Documents the hub shape and `connect` in the README, ONBOARDING (new stage 9, connecting a repository), PRIVACY (what connection records hold, and what `connect` reads), UPGRADING (a v1.3.0 section and the Ctrl-C change), CONTRIBUTING (the Spec Harness re-pin procedure, the `.DS_Store` note and the design decision), ATTRIBUTION, AGENTS and both onboarding skills. Tests check the command and flag names in those documents, the version carriers, the relative and anchor links, the verify line prefixes against the README table, the amended PRIVACY statement, and the stage-9 phrases in `test/onboarding.test.mjs`. They do not check the rest of the prose.
- Version: `VERSION`, `package.json`, the manifest's `templateVersion` and the CLI help move to 1.3.0.
